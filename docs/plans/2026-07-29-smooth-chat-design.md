# SillyTavern 流畅聊天扩展设计说明

## 背景与目标

SillyTavern 在聊天楼层持续增长后，可能同时出现两类性能问题：

1. 浏览器需要维护和排版大量消息节点，导致滚动、输入和切换聊天卡顿。
2. 每次生成携带的历史上下文不断增大，导致首字延迟、请求耗时和费用上升。

本扩展暂定名为 **Smooth Chat（流畅聊天）**，目标是在不删除原始聊天记录的前提下：

- 使用 SillyTavern 原生消息加载上限，只渲染最近一部分消息。
- 每 15 轮对话（1 轮 = 用户消息 + 角色回复，共约 30 条消息）自动生成增量摘要。
- 生成时使用“长期摘要 + 未总结消息 + 最近原文窗口”，减少发送给模型的旧楼层。
- 摘要或扩展故障时安全降级，不阻塞正常聊天、不导致模型静默失忆。
- 支持单人聊天和群聊，允许查看、编辑、暂停和重建摘要。

成功标准：

- 300 条以上消息的聊天仍只渲染配置数量的消息节点。
- 完成首个摘要后，正常生成请求不再持续携带全部已总结消息。
- 原始 `chat` 数据和聊天文件不被扩展删除或覆写。
- 摘要失败、过期或缺失时，不裁剪本次生成的旧消息。
- 切换聊天、刷新页面、编辑/删除/滑动旧消息后状态保持正确。

## 现状与约束

- 项目是一个全新的空 Git 仓库。
- 目标平台是当前 SillyTavern release 分支支持的第三方 UI Extension。
- SillyTavern 已提供稳定的 `SillyTavern.getContext()` API，包括：
  - `generateRaw()`：使用当前后端生成摘要。
  - `chatMetadata` / `saveMetadata()`：保存每个聊天独立的摘要状态。
  - `eventSource` / `event_types`：监听消息和聊天生命周期。
  - `powerUserSettings`：设置 `chat_truncation`。
  - Prompt Interceptor：在本次生成的临时聊天数组中移除已总结消息。
- 扩展不得依赖 Extras、独立服务或数据库。
- 扩展不直接修改 SillyTavern 内部模块导入路径，优先使用 `getContext()`，降低升级破坏风险。
- SillyTavern 内置 Summarize 可能与本扩展重复工作；扩展只提示冲突，不擅自修改其他扩展的设置。

## 方案对比

### 方案一：原生界面截断 + 插件增量摘要（采用）

- 使用 SillyTavern 原生 `chat_truncation` 解决 DOM/渲染卡顿。
- 扩展自行维护增量摘要，并通过 Prompt Interceptor 只裁剪本次模型请求。

优点：

- 不修改聊天记录。
- 能同时改善界面与模型请求性能。
- 使用官方上下文 API，兼容风险可控。
- 失败时可以完全回退到原始上下文。

缺点：

- 需要处理摘要状态、消息变更检测和并发任务。
- 自动总结会产生额外模型调用。

### 方案二：仅配置 SillyTavern 内置功能

- 启用聊天截断和内置 Summarize。

优点：

- 代码量最少。
- 完全依赖原生功能。

缺点：

- 难以精确限制普通回复实际携带的历史消息。
- 无法提供统一的一键状态与安全降级逻辑。

### 方案三：完整自制 DOM 虚拟列表

- 扩展接管消息节点的挂载、卸载和滚动位置恢复。

优点：

- 理论上的页面性能上限最高。

缺点：

- 容易与消息编辑、滑动回复、群聊、其他扩展及 SillyTavern 更新冲突。
- 维护成本明显高于当前需求。

## 推荐方案

采用方案一。界面性能交给 SillyTavern 已有的截断机制，扩展只负责设置、摘要和请求期上下文管理。该方案避免重写聊天渲染器，同时能让生成请求的上下文大小稳定在有限范围内。

## 详细设计

### 架构

扩展由以下文件组成：

- `manifest.json`：扩展元数据、入口脚本、样式和生成拦截器声明。
- `index.js`：初始化、事件订阅、任务调度和设置面板控制。
- `src/state.js`：全局设置、每聊天元数据、迁移与校验。
- `src/summarizer.js`：增量摘要、摘要提示词和任务队列。
- `src/context-manager.js`：请求期摘要注入和已总结消息裁剪。
- `src/performance.js`：原生快速 UI 与聊天显示上限应用/恢复。
- `src/fingerprint.js`：消息规范化与批次指纹计算。
- `settings.html` / `style.css`：扩展设置界面。

### 全局设置

默认设置：

```json
{
  "enabled": true,
  "autoSummarize": true,
  "summaryIntervalRounds": 15,
  "limitRenderedMessages": true,
  "visibleMessageLimit": 60,
  "recentRawRounds": 6,
  "summaryTargetWords": 800,
  "nonBlocking": true,
  "retryDelayMs": 30000
}
```

第一版允许调整自动总结开关、总结间隔、页面消息上限、最近原文轮数和摘要长度。高级失败策略保持内部默认，避免设置面板过载。

### 每聊天状态

状态保存在 `chatMetadata.smooth_chat`：

```json
{
  "schemaVersion": 1,
  "summary": "",
  "summarizedThrough": -1,
  "checkpoints": [],
  "updatedAt": null,
  "status": "idle",
  "lastError": null,
  "paused": false
}
```

每个 checkpoint 包含：

- `endIndex`：该批次结束的消息索引。
- `fingerprint`：该批次所覆盖消息的稳定指纹。
- `summary`：完成该批次后的累计摘要快照。
- `createdAt`：生成时间。

保留摘要快照可以在早期消息发生变化时，仅丢弃受影响 checkpoint 之后的内容，而不是无条件从零开始。

### 消息计数

- 一轮定义为一条正常用户消息和随后一条正常角色回复。
- 系统消息、扩展提示、空消息和错误占位消息不计入轮数。
- 群聊中，一条用户消息后第一条有效角色回复完成一轮；其他连续角色回复仍进入摘要文本，但不额外触发轮数。
- 默认每累计 15 个完整轮次触发一次摘要。

### 摘要流程

1. 在 `CHARACTER_MESSAGE_RENDERED` 或 `GENERATION_ENDED` 后执行轻量检查。
2. 找到上一个 checkpoint 之后新增的完整轮次。
3. 新增轮次达到 15 时，将“上一版累计摘要 + 本批次消息”传给 `generateRaw()`。
4. 提示模型只输出摘要，重点保留：
   - 角色关系、身份和称谓。
   - 已确认事实与世界状态。
   - 重要事件及因果。
   - 当前地点、时间、物品、伤势和资源。
   - 未解决目标、承诺、伏笔和冲突。
   - 对后续回复有影响的语言风格与边界。
5. 校验结果非空、长度合理且不是明显错误文本。
6. 写入新 checkpoint 和累计摘要，再调用 `saveMetadata()`。
7. 若一次积压超过一个批次，逐批排队处理，批次之间让出浏览器主线程。

非阻塞模式在正常角色回复结束后后台运行。若后端拒绝并发，当前任务记为失败并在下一次安全时机重试；不影响用户继续聊天。

### 生成请求上下文

Prompt Interceptor 仅处理正常回复、继续、重试和滑动生成，跳过摘要自身的 raw/quiet 请求。

只有同时满足以下条件时才裁剪：

- 扩展启用且当前聊天未暂停。
- 存在通过校验的摘要。
- checkpoint 指纹仍与当前聊天匹配。
- 没有重建任务或摘要错误。

裁剪逻辑：

1. 计算最后 checkpoint 覆盖的位置。
2. 在已总结区域中额外保留最近 6 轮原文，维持语气和即时细节。
3. 保留 checkpoint 之后所有尚未总结的消息。
4. 从拦截器收到的临时数组中移除更早的消息。
5. 在临时数组最前插入一条系统摘要消息。

原始 `SillyTavern.getContext().chat` 数组和聊天文件不做删除或替换。

### 页面性能

- 扩展不修改 `fast_ui_mode`，避免关闭模糊效果或影响用户自定义主题。
- 将 `powerUserSettings.chat_truncation` 设置为默认 60 条，保存设置并按需刷新当前聊天。
- 用户仍可通过 SillyTavern 原生“显示更多消息”查看旧楼层。
- 扩展首次应用时记录原始值；关闭插件不会静默覆盖用户后来手动修改的值。
- “恢复酒馆默认性能设置”按钮会明确恢复安装前记录值。
- 扩展不向聊天区域插入按钮、状态栏或自定义样式，也不修改气泡、字体、颜色、背景、阴影和布局。

### 设置界面

设置面板包含：

- 总开关。
- 自动总结开关。
- 每 N 轮总结一次，默认 15。
- 页面显示消息数，默认 60。
- 最近原文保留轮数，默认 6。
- 目标摘要长度，默认约 800 字。
- 当前聊天状态：摘要到第几层、距下次摘要还有几轮、最后耗时/错误。
- 操作按钮：
  - 立即总结。
  - 查看/编辑摘要。
  - 重建摘要。
  - 暂停/继续当前聊天。
  - 恢复酒馆原性能设置。

界面使用 SillyTavern 原生 CSS 变量和控件风格，不引入外部 UI 依赖。

### 异常与边界处理

- API 未连接：显示提示，保留全部模型上下文。
- 摘要生成失败：记录错误，延迟重试，不裁剪。
- 摘要结果为空或异常：丢弃结果，不推进 checkpoint。
- 切换聊天：任务携带启动时的 chat ID；写入前再次核对，不把摘要写入新聊天。
- 消息编辑/删除：重新计算 checkpoint 指纹，废弃第一个不匹配 checkpoint 及其后续 checkpoint，进入重建。
- 消息滑动：若影响已总结消息，按编辑处理；否则等待下一批次。
- 重建期间：保留完整请求上下文，重建成功后再恢复裁剪。
- 多次事件触发：同一聊天只允许一个摘要任务，其他请求合并。
- 页面刷新：从 chat metadata 恢复，不依赖仅存在于内存的计数器。
- 群聊：摘要输入带角色名，避免人物归属混淆。
- 内置 Summarize 冲突：检测到可能的摘要注入时只提示一次，由用户决定关闭哪一个。

## 测试策略

### 单元测试

- 轮次识别和系统消息过滤。
- 批次切分与积压处理。
- 消息指纹稳定性。
- checkpoint 校验与失效回滚。
- 上下文裁剪边界。
- 摘要为空、失败、过期时的安全降级。
- 设置迁移和缺省值合并。

### 集成测试

使用模拟的 `SillyTavern.getContext()`：

- 30 条消息后触发一次摘要。
- 60 条消息后生成第二个增量 checkpoint。
- 提示中包含上一摘要和新增批次。
- 原始聊天数组在拦截前后不变。
- 切换聊天时旧任务不能写入新聊天。
- 编辑、删除和滑动触发正确的重建范围。
- 群聊角色名被保留。

### 手工验证

- 在当前 SillyTavern release 版本安装、启用、禁用和重新启用。
- 使用超过 300 条消息的测试聊天检查 DOM 数量、滚动和输入响应。
- 检查正常生成、继续、重试、滑动和群聊生成。
- 模拟断网、API 失败和不支持并发的后端。
- 刷新页面并切换多个聊天，确认摘要隔离。

## 风险与缓解

- 摘要可能遗漏或产生幻觉：允许查看/编辑、保留最近原文、保留全部原始聊天。
- Prompt Interceptor 行为随 SillyTavern 升级变化：仅使用 manifest 声明和 `getContext()`，设置最低客户端版本并提供安全降级。
- 摘要调用增加 token 消耗：每 15 轮一次增量调用，输入只包含上一摘要和新增批次。
- 原生消息加载上限是全局设置：明确展示实际值，保存安装前值，恢复操作必须由用户点击。
- 其他摘要扩展重复注入：检测并提示，不自动篡改第三方配置。
